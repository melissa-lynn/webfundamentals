# Rendering Templates

Imagine a web application that allows you to search for items (such as "yellow shirt"). Maybe the
application is a lost-and-found or a E-commerce site like Ebay, Pinterest, Etsy or zillions of others.
The response page will have your particular search results, maybe structured as a series of `<li>` elements in a list of results, but it will also have a lot of boilerplate elements
that are found on every page: the
logo, the navbar, the logout button and more. Suppose that response page is generated 
by the `/search/` endpoint. Furthermore, those same "boilerplate" elements will be generated by the
`/home/` endpoint and many others. In general, the response web pages from different 
endpoints will (1) have a lot of repeated boilerplate elements and (2) will consist of a 
mixture of dynamic data (like the search results) and static HTML structures. Finally, web
pages are often hundreds of lines of code, and they are in HTML, not Python, so it would
be good to not have them cluttering up our `app.py`. Flask solves addresses these
concerns with *templating*. 

With templating:

* Flask loads a set of templates from files in the `templates` folder when the application starts
* The templates look like HTML files except that there are places where dynamic data can be filled in, and
* the `render_template` function combines dynamic data with the template to create a given response page.

Consider the following trivial example, which has some dynamic data (the current time on the server),
that is combined with a template to create the result.

```python
@app.route('/current-server-time')
def server_time():
    now = datetime.now()
    return render_template('server_time.html', time=now)
```

The template file might look like this:

```html
<!doctype html>
<html lang="en">
<head>
    <meta charset="utf-8">
    <meta name="viewport" content="width=device-width, initial-scale=1">
    <title>Server Time</title>
</head>
<body>

<main>
    <h1>Current time on the Server</h1>

    <p>On the server, it is {{ time }}. </p>

</main>

</body>
</html>
```

There should be nothing surprising in that chunk of HTML except for the following:

```html
{{ time }}
```

The double braces mark a place where dynamic data is filled in. In this case, the 
value of `now` is passed into `render_template` via a keyword argument (`time=now`)
and the `render_template` function fills in the value at the appropriate place.

So far, this is a lot like Python's f-strings, which you are probably familiar with:

```python
@app.route('/current-server-time')
def server_time():
    now = datetime.now()
    print(f'it is currently {now}')  # goes to the terminal, not the browser
    return render_template('server_time.html', time=now)
```

Note that our HTML template is pretty simple (no logos, navbar, logout button, CSS files, and so forth)
and it's still over a dozen lines of code. It's nice to avoid having that clutter up our `app.py`.
The resulting endpoint function is very concise. In a more realistic app, the function might
look up data in a database, based on the logged-in user and the search terms sent from the
browser, and it still won't necessarily be a lot more complex. As the handler becomes more
complicated, all the more reason to keep the HTML out of it.

Flask uses a templating engine called [Jinja](https://jinja.palletsprojects.com/en/stable/templates/).
Jinja is *much* more powerful and versatile than Python f-strings. It has loops, conditionals, filters and more. The following sections will cover the basics. A later section will cover the important topic of *inheritance*. For more information, check the link at the beginning of this paragraph.

## Variables

Before we go further, we want to mention something that can be confusing at first. In the
example above, the template had a variable named `time`. The handler function had a variable 
named `now`. We might just as easily have named that variable `time` as well. If we had, the 
`render_template` call would look like this:

```python
    return render_template('server_time.html', time=time)
```

The `time=time` looks like a tautology, but it's passing the local variable 
named `time` (originally named `now`) into
a template that has a variable also named `time`. It's actually quite common to name things
consistently, such that the `render_template` function has a lot of these seemingly tautological 
arguments.

Note that there are some variables that can be referred to in the template w/o having
to pass them via the arguments to `render_template`. A complete list is [Flask Documentation: Templates Standard Context](https://flask.palletsprojects.com/en/stable/templating/). The
most important ones to know for now are:

* `request` which has information from the browser, such as form data
* `session` which has information we manage. See <xref ref="flask_sessions"/>.
* `url_for()` which allows us to generate in-app URLs. See below.
* `get_flashed_messages()` which allows us to render message to the user. See <xref ref="flask_message_flashing"/>

## Dictionaries

We can pass dictionaries of data into the rendering. For example:

```python
@app.route('/tim/') 
def tim(): 
    art = {'name': 'Arthur, King of the Britons', 
           'quest': 'To seek the grail', 
           'color': 'blue'} 
    return render_template('tim.html', dic = art) 
```

And the template is like this:

```html
<!doctype html>
<html>
    <head>
        <title>Tim</title>
    </head>
    <body>
        <p>Name: {{ dic.name }}. 
        <p>quest: {{ dic.quest }}. 
        <p>favorite color: {{ dic.color }}. 
    </body>
</html>
```

Notice the shortcut syntax (like JavaScript's): you can say `dic.key` instead of `dic['key']`.
The Python syntax, `dic['key']` also works, but `dic.key` is more concise.

## Loops

We often have dynamic data that is a list, such as a list of search results. So, Jinja allows loops.
The following handler passes in a list of favorite things.

```python
@app.route('/things/') 
def things(): 
    favs = ['Raindrops on roses', 
            'whiskers on kittens', 
            'bright copper kettles', 
            'warm woolen mittens', 
            'brown paper packages tied up with strings'] 
    return render_template('things.html', things = favs) 
```

and the template might look like (omitting `doctype`, `html` `head` and other stuff):

```html
        <ul>
            {% for thing in things %}
            <li>{{ thing }}</li>
            {% endfor %}
        </ul>
```

There's some new syntax here. The `for` loop, similar in syntax to Python, is surrounded
by `{% %}` which is Jinja syntax for *statements*. Note that there's an explicit `endfor`
statement, since using indentation to mark the end the loop would be difficult in an HTML
file.

## Conditionals

You might want to choose between two different ways of rendering (part of) a page. For example,
if a user is logged in (`username` is not null) you might want to render a `logout` button, otherwise,
maybe a login form or a link to a login page:

```html
{% if username %}
   <form><button>logout {{username}}</button></form>
{% else %}   
   <a href="/login">Please login</a>
{% endif %}
```

Again, Jinja uses `{% %}` for statements and keywords, here for `if`, `else` and `endif`. 

## Static Files and Urls

In section <xref ref="flask_static"/> we learned about how Flask serves static files
(such as CSS, JS, logo images, and the like) out of a special `static` folder. That
turns out to interact with templates in an important way. For example, our templates
might have a CSS file loaded in the `head`. The template should be written like this:

```html
<!doctype html>
<html lang="en">
<head>
    <meta charset="utf-8">
    <title>Server Time</title>
    <link rel="stylesheet" type="text/css" 
          href="{{ url_for('static', filename='style.css') }}">
</head>
<body>
<main>
    <h1>Current time on the Server</h1>
    <p>On the server, it is {{ time }}. </p>
</main>
</body>
</html>
```

It's tempting to just put the url in there: ```href='/static/style.css'``` but you should
*not*. That's because when the app is deployed, all those urls will (probably) change,
and using `url_for` means Flask can automatically rewrite them for you. See <xref href="url_for"/>
for more information.

Similarly, the example of the conditionals above should really have been written:

```html
{% if username %}
   <form action="{{url_for('logout')}}"><button>logout {{username}}</button></form>
{% else %}   
   <a href="{{url_for('login')}}">Please login</a>
{% endif %}
```

The `url_for` function takes as its argument the name of the handler function for the
endpoint. So, in the example above, we are assuming there are functions named `login`
and `logout` that handle that operation. The URL of the endpoint might or might not match the 
name of the handler function:

```python
@app.route('/logout')
def logout():
    pass

@app.route('/customer-login/')
def login():
    pass
```

## Comments

As your templates get more complicated, you may want to add comments. Of course, you
can use the standard HTML comment syntax: `<!-- comment here -->` but that gets
sent to the browser, and you might not want that. You can put Jinja comments in your
templates, which then get removed when the template is rendered:

```html
<main>
{# vulnerable to CSRF attack; remember to add protections #}
<form action="{{url_for('transaction')}}" method="post">
    <!-- ask user for recipient and amount -->
    ...
</form> 
</main>
```

Comments are often useful in coding and often omitted; use them when appropriate.

## Template Inheritance

If your brain is feeling full and you want to skip this section for now, that would be understandable.
Nevertheless, plan to return to it, because template inheritance is powerful and useful.

As we discussed in the introduction, there can be a lot of repetition in websites. That doesn't
necessarily make them boring, just *consistent*. Every page has a logo, navbar, logout button, etc.
However, if your 
app has the same navbar defined in umpteen template files, and the boss decides to change the navbar,
you have to update all those templates, which *is* boring and, worse, error-prone.

Since it's common for websites to have a basic layout, but then varying *kinds* of pages (maybe some
pages are three-column, or have a side-bar, or a layout with "cards" and so on), Jinja supports
template *inheritance*. 

The idea is straightforward, though there are some tricky bits. There will a *base* template, and *child* templates. The base template is just like the templates we've been describing, and they
will look like a complete HTML page. Here's an example. 

```html
<!doctype html>
<html lang="en">
<head>
    <meta charset="utf-8">
    <title>Server Time</title>
    <link rel="stylesheet" type="text/css" 
          href="{{ url_for('static', filename='style.css') }}">
</head>
<body>
  <header>
    <a href="{{url_for('home')}}">
      <img src="{{url_for('static','logo.png')}}" alt="our logo">
    </a>

    <nav>
      <a href="{{url_for('home')}}">home</a>
      <a href="{{url_for('about')}}">about</a>
    ...
    </nav>
  </header>

  <main>
    {% block main %}
    <h1>Page title</h1>
    <p>The content specific to this page...</p>
    {% endblock %}
</main>

  <footer>
    &copy; 2026 By TIC
  </footer>
</body>    
</html>
```

The main difference above is the `block main` and `endblock` that surround the contents
of the `<main>` element. That allows a *child* template to replace that named block.
For example, suppose that the template above is saved in `base.html`; 
we could have the following child template for our server time:

```html
{% extends "base.html" %}

{# replaces main content block #}
{% block main %}
    <h1>Current time on the Server</h1>

    <p>On the server, it is {{ time }}. </p>
{% endblock %}
```

This child template is *much* simpler to read and understand. It declares that it extends the 
base template called `base.html` and then replaces just the block named `main`. It will
*inherit* all the other HTML. If we suppose that the child template is called `time.html`, 
the rendering looks like this:

```python
@app.route('/current-server-time')
def server_time():
    now = datetime.now()
    return render_template('time.html', time=now)
```

which is essentially the same as our original. So, template inheritance (1) avoids a lot
of copy/pasting of HTML code, (2) simplifies the child templates, and (3) doesn't affect
our `render_template` call at all.

## App File Organization

In this section, we've learned about templates, which are external files, and in the previous section, we learned about static files, which are also external. So, you might be getting a bit confused about the structure of a Flask app. Here's the directory structure of a simple Flask app:

```sh
myapp/
    app.py
    static/
        style.css
        logo.png
    templates/
        base.html
        time.html
```

Additional Python modules would go in the `myapp` folder, next to the `app.py`, which is where
our `@app.route()` calls go.

## Summary {#flask_template_summary}

Templating is an important and powerful part of any web framework. Flask uses Jinja. We learned:

* templates are separate files that go in the `templates` subfolder of our app
* templates have places where dynamic data can be filled in: `{{ var}}`
* keys in dictionaries can be accessed with dot notation: `{{ dic.key }}`
* templates can have statements:
    - loops can be done like `{% for elt in var %}` and `{% endfor %}`
    - conditionals can be done like `{% if expr %}` `{% else %}` and `{% endif %}`
* templates can also have comments: `{# like this #}`
* templates are rendered with `render_template('templ.html', var1=val1, var2=val2)`

We also learned about template inheritance:

* the base template is normal, except that it has named blocks:
    - `{% block block_name %}`
    - `{% endblock %}`
* the child can *replace* a named block:
    - `{% extends "base.html" %}`
    - `{% block block_name %}`
    - `{% endblock %}`
